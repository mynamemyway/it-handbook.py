## 0. Основные положения

### Хороший стиль
- **snake_case**: имена столбцов, таблиц и функций в нижнем регистре с подчеркиваниями
- **Идентификаторы и имена**: осмысленные и в едином стиле
- **Пробелы и отступы**: логично расставленные для лучшей читаемости кода
- **Дата и время**: стандарт ISO 8601: `YYYY-MM-DD HH:MM:SS`
- **Функции SQL**: стандартные ANSI вместо специфичных для поставщика — для переносимости
- **Код**: лаконичный, без лишних кавычек, скобок и неуместного `WHERE`
- **Комментарии**: `--` для однострочных, `/* ... */` для блочных

```sql
SELECT file_hash -- stored ssdeep hash
FROM file_system
WHERE file_name = '.vimrc';

/* Updating the file record after writing to the file */
UPDATE file_system
SET file_modified_date = '1980-02-22 13:19:01.00000',
    file_size = 209732
WHERE file_name = '.vimrc';
```

### Плохой стиль
- **camelCase**: неудобочитаем
- **Префиксы и венгерская нотация**: `sp_`, `tbl_` избыточны
- **Множественное число**: лучше собирательные понятия — `staff` вместо `employees`
- **Идентификаторы в кавычках**: если неизбежны — двойные кавычки по SQL-92
- **Принципы ООП**: не применяются к SQL и структуре базы данных

## 1. Соглашения о наименовании

### Общее
- Имя уникально и не совпадает с зарезервированными ключевыми словами.
- Длина имени — до 30 символов (софт-лимит; современные СУБД допускают больше).
- Имя начинается с буквы и не заканчивается `_`.
- Допустимые символы: буквы, цифры, `_`.
- Избегайте нескольких `_` подряд.
- `_` ставится там, где в реальной жизни был бы пробел.
- Избегайте сокращений. Если используете — они должны быть общепонятны.

```sql
SELECT first_name
FROM staff;
```

### Таблицы
- Собирательные имена или множественное число: `staff` > `employees`.
- Без префиксов `tbl_` и венгерской нотации.
- Название таблицы не совпадает с названием ни одного из её столбцов.
- Не объединяйте названия двух таблиц в имени таблицы отношений. Вместо `cars_mechanics` → `services`.

### Столбцы
- Названия в единственном числе.
- Название столбца не совпадает с названием таблицы.
- Названия со строчной буквы. Исключение — имена собственные.
- Не используйте `id` как имя первичного ключа — лучше `employee_id`*

#### 📝 Именование первичных ключей (PK): два подхода

Существуют две практики проектирования БД. Выбор зависит от архитектуры проекта.

1. **Универсальное именование**: `id`
  - Дефолт ORM и фреймворков: Django, Rails, Laravel, SQLAlchemy.
  - Плюс: коротко, генераторы кода и миграции ожидают именно это.
  - Минус: неоднозначность. `SELECT * FROM book JOIN author` вернёт две колонки с именем `id` — придётся алиасить. В логах, BI и аналитике голый `id` ни о чём не говорит.

2. **Семантическое именование**: `table_id` (`employee_id`)
  - Конвенция «чистого SQL», DBA и data engineering (Holywell, Celko, DWH-команды).
  - Плюсы:
    - колонка сама себя документирует в любой выборке;
    - внешний ключ получает то же имя, что и первичный → можно писать `JOIN book USING (book_id)` вместо `ON book.id = ba.book_id`;
    - сквозная согласованность схемы: одно имя — один тип — один смысл во всей базе.

**Ключевой нюанс**: в подходе с `id` внешний ключ называют `employee_id`. То есть там асимметрия: PK = `id`, FK = `employee_id`. В подходе с семантикой PK и FK симметричны — это и есть *согласованность по типу и имени во всей схеме*.

**Стандарт**
**Промышленное правило**: одна конвенция на проект, соблюдается строго.
**Сферы применения различаются**:
- Бэкенд на ORM → `id` допустим, фреймворк этого ждёт;
- Чистый SQL, аналитика, DWH, твой курс → `table_id`.

**Рекомендация как универсальной привычки**:
`table_id` работает в обоих мирах (ORM можно настроить на кастомное имя PK), а наоборот — нет.

#### 📝 Связь таблиц в Python-стиле (Стандарт для Backend)

В веб-разработке на Python принято комбинировать эти подходы для связи таблиц «один ко многим»:

- **Первичный ключ (PK)** именуется: `id`.
- **Внешний ключ (FK)** в связанной таблице по схеме: `имя_таблицы_id`.

**Пример структуры таблиц:**
1. Таблица `departments` (Департаменты):
  - `id` (PK) — уникальный номер департамента
  - `name` — название
2. Таблица `employees` (Сотрудники):
  - `id` (PK) — уникальный номер сотрудника
  - `first_name` — имя
  - `department_id` (FK) — ссылка на родительский департамент (`departments.id`)

**Пример JOIN-запроса в этом стиле:**
```sql
SELECT e.first_name, d.name
FROM employees AS e
INNER JOIN departments AS d ON e.department_id = d.id;
```

### Псевдонимы / корреляции
- Связаны с объектом или выражением, псевдонимом которого являются.
- Составляются из первых букв слов имени объекта.
- При конфликте имён добавляется цифра.
- Всегда через `AS`.
- Для агрегатов (`SUM()`, `AVG()`) — имя, как если бы это был столбец таблицы.

```sql
SELECT first_name AS fn
FROM staff AS s1
JOIN students AS s2
    ON s2.mentor_id = s1.staff_num;

SELECT SUM(s.monitor_tally) AS monitor_total
FROM staff AS s;
```

### Хранимые процедуры
- Имя содержит глагол.
- Без префиксов `sp_` и венгерской нотации.

### Универсальные суффиксы
`_id`     — уникальный идентификатор, например первичный ключ
`_status` — флаг или статус, например `publication_status`
`_total`  — общее количество или сумма значений
`_num`    — поле, содержащее число
`_name`   — любое имя, например `first_name`
`_seq`    — непрерывная последовательность значений
`_date`   — колонка с датой
`_tally`  — счётчик
`_size`   — размер или величина чего-либо
`_addr`   — физический или абстрактный адрес, например `ip_addr`

## 2. Синтаксис запросов

### Зарезервированные слова
- Ключевые слова всегда UPPERCASE: `SELECT`, `WHERE`, `JOIN`.
- Полный вариант вместо сокращённого: `ABSOLUTE`, не `ABS`.
- ANSI SQL вместо vendor-specific — для переносимости.

```sql
SELECT model_num
FROM phones AS p
WHERE p.release_date > '2014-09-30';
```

### Пробельные символы

#### Пробелы
- Ключевые слова (`SELECT`, `FROM`, `WHERE`, `JOIN`) выравниваются **по левому краю**.
  Это современный стандарт, принятый в `sqlfluff`, `dbt`, Google SQL Style Guide.
- Содержимое клаузы (столбцы, условия) — **фиксированные 4 пробела** (как в Python).
  Каждый уровень скобок (подзапрос, тело CTE) добавляет ещё +4.
- `AND` / `OR` — на том же уровне, что и первое условие клаузы.
- Пробелы ставятся:
  - до и после `=`
  - после запятых
  - вокруг операторов сравнения

```sql
(SELECT f.species_name,
    AVG(f.height) AS average_height,
    AVG(f.diameter) AS average_diameter
FROM flora AS f
WHERE f.species_name = 'Banksia'
    OR f.species_name = 'Sheoak'
    OR f.species_name = 'Wattle'
GROUP BY f.species_name, f.observation_date)

UNION ALL

(SELECT b.species_name,
    AVG(b.height) AS average_height,
    AVG(b.diameter) AS average_diameter
FROM botanic_garden_flora AS b
WHERE b.species_name = 'Banksia'
    OR b.species_name = 'Sheoak'
    OR b.species_name = 'Wattle'
GROUP BY b.species_name, b.observation_date);
```

**Примечание**:
> ⚠️ Холиуэлл выравнивает ключевые слова по **правому** краю («коридор»).
> Современный мейнстрим (Google SQL, dbt, sqlfluff) — по **левому**.

#### Переводы строки
Всегда делайте перенос:

- перед `AND` или `OR`
- после `;` (разделение запросов)
- после каждого основного ключевого слова
- после запятой при логических группах столбцов

```sql
INSERT INTO albums (title, release_date, recording_date)
VALUES
    ('Charcoal Lane', '1990-01-01 01:01:01.00000', '1990-01-01 01:01:01.00000'),
    ('The New Danger', '2008-01-01 01:01:01.00000', '1990-01-01 01:01:01.00000');

UPDATE albums
SET release_date = '1990-01-01 01:01:01.00000'
WHERE title = 'The New Danger';

SELECT
    a.title,
    a.release_date,
    a.recording_date,
    a.production_date -- grouped dates together
FROM albums AS a
WHERE
    a.title = 'Charcoal Lane'
    OR a.title = 'The New Danger';
```

#### JOIN
Объединения выравниваются по левому краю, условия `ON` — с отступом 4.

```sql
SELECT
    r.last_name
FROM riders AS r
INNER JOIN bikes AS b
    ON r.bike_vin_num = b.vin_num
    AND b.engine_tally > 2
INNER JOIN crew AS c
    ON r.crew_chief_last_name = c.last_name
    AND c.chief = 'Y';
```

#### Подзапросы и CTE
Подзапросы форматируются по тем же правилам, что и основной запрос:
- Тело в скобках получает +4 к отступу.
- Закрывающая скобка — на новой строке, по уровню начала блока, который она закрывает.

Скобки вокруг веток `UNION` — группировка, а не вложенность:
- Ветку форматируем как обычный запрос, скобки клеим к `SELECT` и последней строке.
- +4 — только для реальных подзапросов внутри внешнего запроса.

Для читаемости предпочитайте **CTE** (`WITH ... AS`) вложенным подзапросам:

```sql
WITH confirmed_champions AS (
    SELECT
        last_name,
        MAX(YEAR(championship_date)) AS last_year
    FROM champions
    WHERE
        confirmed = 'Y'
        AND YEAR(championship_date) > 2008
    GROUP BY last_name
)
SELECT
    r.last_name,
    c.last_year AS last_championship_year
FROM riders AS r
INNER JOIN confirmed_champions AS c
    ON c.last_name = r.last_name;
```

### Формальные тонкости
- `BETWEEN` вместо нагромождения `AND`.
- `IN()` вместо цепочки `OR`.
- `CASE` для условной интерпретации значений и сложных логических структур.
- Избегайте `UNION` и временных таблиц без необходимости.

```sql
SELECT
    CASE postcode
        WHEN 'BN1' THEN 'Brighton'
        WHEN 'EH1' THEN 'Edinburgh'
    END AS city
FROM office_locations
WHERE
    country = 'United Kingdom'
    AND opening_time BETWEEN 8 AND 9
    AND postcode IN ('EH1', 'BN1', 'NN1', 'KW1');
```

## 3. Синтаксис CREATE

При разработке схемы данных создавайте человекочитаемый код.
Объявления столбцов логически структурированы и сгруппированы.
Отступ внутри `CREATE TABLE` — **4 пробела**.

### Типы данных
- Стандартные ANSI-типы вместо vendor-specific — для переносимости.
- Для точной арифметики (деньги, координаты) — `NUMERIC` / `DECIMAL`.
- `FLOAT` и `REAL` дают ошибки округления из-за двоичного представления.

### Значения по умолчанию
- Тип `DEFAULT` совпадает с типом столбца.
  Для `DECIMAL`-столбца: `DEFAULT 0.00`, не `DEFAULT 0`.
- Порядок в объявлении: тип → `DEFAULT` → `NOT NULL`.

### Ограничения и ключи

#### Ключи
Выбор ключей обоснован — от них зависит производительность и целостность данных.

- Ключ уникален.
- Тип данных ключа одинаков во всей схеме (и в `PRIMARY KEY`, и в `FOREIGN KEY`).
- Значение ключа не меняется со временем.
- Ключ как можно проще — это удешевляет составные внешние ключи и индексы.
- Проверяйте значение на соответствие стандарту (например, ISO), если применимо.

#### Ограничения

**Общее**
- У каждой таблицы есть хотя бы один ключ.
- Ограничениям присваиваются вразумительные имена.
  Для `UNIQUE`, `PRIMARY KEY`, `FOREIGN KEY` имена создаются автоматически;
  для остальных (`CHECK`) — именуйте вручную.

**Расположение и порядок**
- `PRIMARY KEY` объявляется первым, сразу после `CREATE TABLE`.
- Ограничение столбца (`NOT NULL`, `DEFAULT`, `CHECK`) — в той же строке, сразу после типа.
- Ограничения, затрагивающие несколько столбцов, — в конце тела `CREATE TABLE`.
- Ограничения целостности уровня таблицы — в конце.
- В `FOREIGN KEY`: `ON DELETE` перед `ON UPDATE` (алфавитный порядок).
- Выравнивайте типы данных и `NOT NULL` по одной вертикальной позиции для читаемости.

**Валидация**
- `LIKE` / `SIMILAR TO` для строк с известным форматом.
- `CHECK()` для ограничения диапазона числовых значений (обычно > 0).
- `CHECK()` оформляется как отдельное именованное ограничение — для упрощения отладки.

**Пример**
```sql
CREATE TABLE staff (
    PRIMARY KEY (staff_num),
    staff_num      INT(5)       NOT NULL,
    first_name     VARCHAR(100) NOT NULL,
    pens_in_drawer INT(2)       NOT NULL
        DEFAULT 1
        CONSTRAINT pens_in_drawer_range
        CHECK (pens_in_drawer BETWEEN 1 AND 99)
);
```

## 4. Чего следует избегать
- Не применяйте ООП-паттерны к реляционной модели базы данных.
- Не разносите значения и единицы измерения по разным столбцам.
  Единицы должны быть очевидны из имени столбца; корректность — через `CHECK()`.
- Избегайте паттерна EAV (Entity-Attribute-Value).
  Для неструктурированных данных используйте специализированные хранилища (JSONB, document DB).
- Не разбивайте данные одной логической таблицы по разным таблицам
  на основании условностей (архивация по времени, географические атрибуты).
  Это приводит к частому `UNION` вместо простых запросов к одной таблице.
