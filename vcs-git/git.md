## 1. Git Merge
В коммерческой разработке используют два подхода к обновлению своей ветки (когда в main ушел чужой код, а мне надо дописать фичу):

1. **git merge main** (Через слияние). Git берет изменения из main и насильно вливает в вашу ветку. Появляется уродливый технический «коммит слияния» (Merge commit). История становится похожа на запутанное дерево.
2. **git rebase main** (Через перебазирование). Git временно «отрезает» ваши новые коммиты, скачивает свежий код из main, а затем приклеивает ваши коммиты сверху. История получается идеально ровной, будто вы только что начали писать код на базе самого свежего проекта.

## 2. Какие инструменты Git используют в компаниях?
В реальной работе используется стандартный стек:

- Ветки по Git Flow или GitHub Flow: Есть главная ветка (main или master), ветка разработки (develop) и короткие ветки под задачи (feature/task-123, bugfix/fix-login).
- Pull Requests (или Merge Requests в GitLab): Код никогда не льется в main напрямую. Всегда создается PR, его смотрят коллеги (Code Review), проходят автоматические тесты (CI/CD), и только потом код мержится.
- Инструменты автоматизации: Пулл-реквесты на GitHub часто настраивают так, чтобы кнопка «Merge» блокировалась, пока код не обновится до актуального состояния main. Вот тут rebase или автоматический squash and merge и приходят на помощь.

## 3. Обязательно ли учить консоль или можно сидеть на UI (GitHub Desktop)?
- 90% ежедневных задач (add, commit, push, pull, создание веток) в GUI-интерфейсе делаются быстрее и нагляднее.
- Консоль нужно знать на базовом уровне («понимать, как это работает под капотом») по двум причинам:

   1. Сложные конфликты и факапы: если случайно закоммичен токен от базы данных, в консоли через git reflog или git reset --hard можно спасти проект за секунду.
   2. На интервью спросят: «В чем разница между merge и rebase?» или «Что делает git cherry-pick?».

* Нужно знать: Разницу между merge и rebase, что такое stash (заначка), как решать конфликты, как делать amend (исправление последнего коммита).

## 4. В какой ветке работать

**Правило:** писать код напрямую в ветку develop (или main) **нельзя**.
В develop всегда должен лежать стабильный, рабочий код, который в любой момент можно запустить.

**Как выглядит правильный процесс:**

   1. Переключаетесь на develop и скачиваете последние изменения команды (git pull).
   2. Отпочковываетесь от нее — создаете свою ветку под задачу (например, feature/login-page или bugfix/fix-Header).
   3. Кодите, делаете коммиты и пушите только в эту свою ветку.
   4. Когда задача полностью готова, вы создаете Pull Request (PR) из своей ветки в develop.
   5. Коллеги проверяют ваш код, и если всё ок, ваша ветка сливается (merge или rebase) в develop. Саму ветку под задачу после этого удаляют.

## 5. Можно ли сделать Rebase (Перебазирование) на самом GitHub, а не в консоли?
В момент принятия Пулл-Реквеста (PR / MR), варианты принятия:

- Create a merge commit (обычный мерж — то, что вы делали).
- Squash and merge (схлопывает все ваши мелкие коммиты в один и вливает в main).
- Rebase and merge (это и есть тот самый rebase! GitHub сам берет ваши коммиты и перебазирует их поверх актуального main, не создавая лишних коммитов слияния).

В консоли ребейз делают до создания PR, чтобы стянуть изменения из develop в свою ветку, решить конфликты локально на компе, убедиться, что проект собирается, и только потом заливать чистую ветку на GitHub.

## 6. Что делать с веткой после Merge (Слияние)?

Продолжать работу в старой ветке — это плохой тон (и технические грабли).
Когда вашу ветку влили в develop на GitHub, её миссия завершена. Если вы продолжите писать новый код в этой же ветке, у вас гарантированно возникнут проблемы:

   1. Вы запутаете коллег, потому что в Пулл-Реквесте смешаются старые (уже принятые) задачи и новый код.
   2. Начнутся дикие конфликты, так как ветка на сервере закрыта, а у вас на компьютере она живет своей жизнью.

Как это устроено в Git (про дубликаты веток):
Ветка в Git — это текстовый ярлык (ссылка) на конкретный коммит. Когда вы нажимаете кнопку "Delete branch" на GitHub после мержа, удаляется только ярлык на сервере. На компьютере этот ярлык (feature/...) остается, пока вы не удалите его вручную или через интерфейс.

Дубликатов не возникнет: если вы удалили ветку на сервере, стерли её локально и потом создали новую с таким же именем — для Git это будет абсолютно чистая новая ветка, созданная с нуля.

## 7. Сценарий использования Stash (Тайник)

В процессе написания кода может возникнуть ситуация, когда нужно срочно переключиться на другую ветку (использовать git checkout) — или, например, внести правки, которые относятся к другой задаче. Однако новые изменения еще не готовы к тому, чтобы их коммитить и добавлять в репозиторий, — при этом терять их нельзя. В таком случае, как и во многих других, полезной окажется команда git stash.

Git stash перемещает текущие изменения (так называемые local changes) в локальную директорию, которая выполняет роль специального хранилища, то есть скрывает эти изменения, сохраняя их отдельно, с опцией вернуть позже, когда это понадобится. Таким образом, файлы рабочей копии возвращаются к своему исходному состоянию. Внесенные изменения помещаются в стек, после чего их можно легко оттуда извлечь. Важно отметить, что в рабочей копии исчезнут все измененные файлы, — независимо от того, добавлены они в индекс или нет.

После выполнения этой строки все несохраненные изменения будут сохранены, но не закоммичены. Эти отложенные участки будут сохранены в локальном репозитории и при выполнении команды git push не будут переданы на сервер. Такие изменения иногда называют «прятанья».

**Stash сохраняет незакоммиченный код (Fork -> вкладка Local Changes)**
  1. Вы переписали функцию, протестировали, сделали коммит.
  2. Вы начали писать следующую функцию, но не закончили, Zed подчеркивает красным, код не работает.
  3. СРОЧНО нужно переключиться на другую ветку, чтобы починить баг.

**Варианты:**
  1. без Stash (костыль): Временный коммит (work in progress), чтобы переключить ветку или отменить изменения.
  2. со Stash (чистый): Нажать Stash. Незакоммиченный код уходит в сейф, файл чистый (в состоянии последнего коммита). Вы уходите чинить баг. Возвращаетесь, делаете Pop Stash, продолжаете писать незаконченную функцию.

**Если рабочая ветка отстает от main** (например после починки бага мной или другим человеком)
  1. Вы закоммитили свои файлы (пуш не делали)
  2. Переключились на main, починили баг
  3. Сделали пуш фикса на GitHub - ветка main на сервере ушла вперед.

## 7.1 Git Stash Cheatsheet

```bash
git stash                  # Спрятать все изменения (tracked файлы) в стек
git stash save "msg"       # Спрятать с комментарием (устаревает, лучше push)
git stash push "msg"       # Современный аналог save, поддерживает пути
git stash -u               # Спрятать также неотслеживаемые (untracked) файлы
git stash -a               # Спрятать всё, включая игнорируемые (.gitignore) файлы
git stash pop              # Достать последние изменения и удалить из стека
git stash apply            # Достать изменения, но оставить копию в стеке
git stash list             # Показать список всех спрятанных изменений
git stash show             # Показать статистику изменений последнего stash
git stash show -p          # Показать дифф (различия) последнего stash
git stash drop             # Удалить последний stash из списка
git stash clear            # Очистить весь стек stash
git stash branch <name>    # Создать новую ветку из последнего stash
git stash -p               # Интерактивный выбор частей кода для stash
```

## 8. Как это сделать в Fork с использованием Rebase
  1. Переключаетесь на локальную ветку main и забираете свежий фикс с сервера через кнопку Pull.
  2. Переключаетесь обратно на свою рабочую ветку.
  3. В левом меню Fork находите ветку main, кликаете по ней правой кнопкой мыши и выбираете Rebase on `main`.

**Что сделает Git:**
  1. Временно отложит все коммиты, которые вы успели сделать до ухода на баг в `main`
  2. Прилепит снизу свежий фикс из `main`
  3. А ваши коммиты положит сверху.
  4. История станет идеально ровной, без единого лишнего технического мерж-коммита.
  5. Вы можете тестировать фичу дальше и спокойно пушить.

## 9. Что такое Stage? (Индекс, Сцена, Этап)
Stage (или Staging Area) — это «сцена» или промежуточный буфер, куда вы откладываете файлы, которые готовы пойти в следующий коммит.
В консоли Git это соответствует команде git add.

**В Fork процесс коммита разделен на два этапа для максимального контроля, когда нажимаете Stage:**
   1. Файл перемещается из списка Unstaged (изменено на диске) в список Staged (подготовлено к сохранению).
   2. Теперь, когда вы напишете текст коммита и нажмете кнопку Commit, Git сохранит только те файлы (строки), которые вы перенесли на Stage. Всё, что осталось в Unstaged, в коммит не попадет и останется ждать своей очереди.

**Выборочный Stage (Stage Lines / Stage Hunks)**
   1. Кликните по файлу в Local Changes.
   2. В окне диффа справа выделите мышкой только те строки, которые относятся к одной правке.
   3. Нажмите кнопку Stage Lines (или Stage Hunk).
   4. Выбранная часть улетела на «сцену» (в коммит), а вторая половина осталась в Unstaged.
   5. Вы делаете коммит только для выбранной части.
   6. Затем берете оставшийся кусок кода и делаете для него второй отдельный коммит.

## 10. Управление аккаунтом и доступом к репозиторию

1. **В личных проектах гибких ролей нет.**
  - Если ваш проект публичный (Public), его может увидеть любой гость по ссылке — приглашать не нужно.
  - Если ваш проект приватный (Private), то пригласить человека можно только как полноценного соавтора (Collaborator с Write-доступом).

2. **Если вы создали бесплатную Организацию (Organization)**
Если вам нужен строгий контроль прав как в GitLab, вы можете прямо на GitHub бесплатно создать организацию (кнопка + вверху справа → New organization). В репозиториях организации при приглашении людей появляется выбор из 5 стандартных ролей:

  - **Read** (Чтение) — аналог гостя. Человек может зайти, посмотреть, скачать код, почитать обсуждения, но ничего не может запушить. Это идеальная роль для демонстрации кода.
  - **Triage** (Триаж) — для тех, кто менеджерит проект (может закрывать чужие тикеты, вешать лейблы), но сам код не пишет.
  - **Write** (Запись) — стандартная роль для разработчика в команде (можно пушить код в ветки).
  - **Maintain** (Управление) — для тимлидов (можно настраивать правила веток, доступы, защищать main от прямого пуша).
  - **Admin** (Админ) — полный доступ, включая удаление репозитория.

## 11. Работа с удалёнными репозиториями (git remote)
Все команды ниже выполняются строго внутри папки проекта. Они управляют связью между компьютером и сервером (GitHub/GitLab).

  - `git remote` — показывает короткие имена (псевдонимы) удалённых серверов, к которым привязан этот проект. В 99% случаев вы увидите только одно имя — origin (так Git по умолчанию называет главный репо в сети).
  - `git remote -v` — то же самое, но полезнее: показывает реальные URL-ссылки для чтения (fetch) и записи (push). Нужна, чтобы быстро проверить, в тот ли репозиторий на GitHub улетит ваш код.
  - `git ls-remote origin` — заглядывает на сервер (например, GitHub) без скачивания самого кода и показывает актуальный список веток и коммитов, которые сейчас там лежат.

## 12. Скачивание кода и разница между Git Fetch и Git Pull

Существуют 4 команды для получения кода из удаленного репозитория (сервера):

1. `git clone` — Полное копирование.
  - Скачивает весь репозиторий с нуля на локальный компьютер.
  - Фиксирует настройки и автоматически устанавливает ветку по умолчанию (обычно `main` или `master`).

2. `git remote update` — Глобальное обновление связей.
  - Обновляет данные обо всех удаленных подключениях (если у вас в проекте привязано несколько разных серверов/репозиториев).

3. `git fetch` — Безопасное скачивание истории изменений.
  - Скачивает с сервера новые коммиты, хэши и ветки, но **не внедряет их в ваш текущий рабочий код**.
  - Как это работает:
    * **Сетевое взаимодействие**: Общается с сервером по протоколу Git.
    * **Ветки отслеживания**: Записывает скачанную информацию в локальные копии удаленных веток (например, в `origin/main`). Вы видите, что изменилось на сервере, но код на компьютере локально не меняется.
    * **Слияние изменений**: Чтобы внедрить изменения в рабочую ветку, после `git fetch` нужно вызвать `git merge` или `git rebase`.
    * **Опции**: С помощью флагов можно настроить команду (например, автоматически удалять ссылки на ветки, которые уже удалены на самом GitHub).

4. `git pull` — Автоматическое скачивание + слияние.
  - Это комбинированная команда. Работает как быстрая связка двух шагов за один раз: 
    `git pull` = `git fetch` + `git merge`.
  
**Главное отличие одной фразой:** 
`git fetch` — это просто *посмотреть* и скачать историю (безопасно для вашего кода), а `git pull` — это скачать и сразу *применить* (могут возникнуть конфликты слияния).

### Справочник команд скачивания кода

```bash
git clone <url>            # Полностью скопировать удаленный репозиторий на ПК "с нуля"
git remote update          # Обновить состояние веток для ВСЕХ удаленных подключений
git fetch                  # Скачать историю изменений с дефолтного сервера (origin)
git fetch <remote>         # Скачать историю с конкретного указанного сервера
git fetch --all            # Скачать данные со всех привязанных серверов (аналог remote update)
git fetch --prune          # Скачать изменения и удалить локальные ветки, которых больше нет на сервере
git fetch --depth=<n>      # Скачать только последние N коммитов для экономии трафика/времени
git pull                   # Автоматически скачать изменения и сразу влить в рабочую ветку (fetch + merge)
git pull --rebase          # Скачать изменения и применить их через rebase вместо merge-коммита
```

## 13. Дополнительно

### 1. Выборочный перенос коммитов (git cherry-pick)

- Зачем нужно: Представьте, что ваш коллега в своей ветке написал крутую функцию или исправил баг. Вам нужен только этот конкретный фикс в свою ветку, а не всю ветку.
- Как решать: Вы берете хэш этого коммита и копируете строго его:

```bash
git cherry-pick <хэш_коммита>
```

### 2. Поиск коммита, который всё сломал (git bisect)

- Зачем: В проекте что-то сломалось. Месяц назад работало, а сейчас — нет. За это время написали 200 коммитов.
- Как решать: Git умеет искать баг методом бисекции (делением истории пополам). Вы говорите: «Тут всё плохо, а месяц назад на этом коммите всё было хорошо». Git сам начинает переключать вас по коммитам, спрашивая, работает код или нет. За 6-7 шагов вы найдете точный коммит, где сломался код.

```bash
git bisect start
git bisect good <хэш_коммита_который_работает>
git bisect bad <хэш_коммита_который_не_работает>
git bisect run <команда_для_проверки>
```

### 3. Интерактивный rebase (git rebase -i)

- Зачем: Перед отправкой ветки на проверку (Code Review) вы хотите причесать свою историю коммитов. Например, объединить 5 мелких коммитов вроде "исправил опечатку", "забыл точку с запятой" в один красивый коммит "Реализовал логику авторизации".
- Как решать: Команда `git rebase -i HEAD~5` открывает интерактивное меню, где можно переименовывать, удалять или склеивать коммиты между собой.

## 🎯 Саммари для работы с Git

1. Перед тем как начать писать код, делай `git fetch` (или `git pull`).
2. Один коммит — одна задача или фикс. Не смешивай разные правки.
3. Никогда не делай `git push --force` в общие ветки (`main`, `master`, `develop`).
4. Для переключения веток без коммита незавершенного кода используй `git stash`.
5. Не коммить в общие ветки напрямую — всегда создавай под задачу отдельную ветку (`feature/имя`).
6. Перед отправкой ветки на сервер делай `git rebase main` (или `develop`), чтобы влить актуальный код коллег.
7. Всегда проверяй `git status` перед тем, как набрать `git add .`, чтобы не закинуть в индекс мусор или логи.

## 🛠️ Справочник Git-команд для реальной практики

#### Настройка и старт
```bash
git init                   # Инициализировать репозиторий в текущей папке
git clone <url>            # Склонировать существующий проект с сервера
git config --global user.name "Имя"   # Настроить имя автора коммитов
git config --global user.email "mail" # Настроить email автора
```

#### Индекс и коммиты
```bash
git status                 # Показать статус файлов (изменено/в индексе)
git diff                   # Посмотреть изменения в коде до добавления в индекс
git add .                  # Добавить ВСЕ изменения в индекс
git add <путь_к_файлу>     # Добавить в индекс конкретный файл
git commit -m "msg"        # Создать коммит с комментарием
git commit --amend -m "msg"# Переписать сообщение последнего локального коммита
```

#### Ветки
```bash
git branch                 # Список локальных веток
git branch -a              # Список всех веток (локальные + серверные)
git checkout <ветка>       # Перейти на указанную ветку
git checkout -b <ветка>    # Создать новую ветку и сразу перейти на нее
git branch -d <ветка>      # Удалить локальную ветку (после слияния)
```

#### Слияние и перенос (Merge & Rebase)
```bash
git merge <ветка>          # Влить указанную ветку в текущую (с merge-коммитом)
git rebase <ветка>         # Перенести текущую ветку поверх указанной (линейная история)
git rebase --continue      # Продолжить rebase после ручного разрешения конфликта
git rebase --abort         # Полностью отменить rebase при ошибке
```

#### Временное хранение (Stash)
```bash
git stash                  # Спрятать все изменения (tracked) в стек
git stash push -m "msg"    # Спрятать изменения с комментарием
git stash list             # Посмотреть список всех заначек
git stash pop              # Достать последние изменения и применить к коду
git stash drop             # Удалить последнюю заначку из стека
```

#### Работа с сервером
```bash
git remote -v              # Проверить URL-адреса удаленного репозитория
git fetch --prune          # Скачать историю с сервера и почистить удаленные ветки
git pull                   # Скачать изменения с сервера и сразу влить в свой код
git push origin <ветка>    # Отправить локальную ветку на сервер впервые
git push                   # Отправить коммиты в уже связанную ветку
```

#### Просмотр истории и отмена
```bash
git log --oneline          # История коммитов в компактном виде (1 строка = 1 коммит)
git restore <файл>         # Отменить незакоммиченные изменения в файле
git reset --soft HEAD~1    # Отменить последний коммит (изменения остаются в коде)
git reset --hard HEAD~1    # Жестко удалить последний коммит и все изменения (опасно!)
```
