# Базовые понятия

## 1. Git Merge
В коммерческой разработке используют два подхода к обновлению своей ветки (когда в main ушел чужой код, а мне надо дописать фичу):

1. **git merge main** (Через слияние). Git берет изменения из main и насильно вливает в вашу ветку. Появляется уродливый технический «коммит слияния» (Merge commit). История становится похожа на запутанное дерево.
2. **git rebase main** (Через перебазирование). Git временно «отрезает» ваши новые коммиты, скачивает свежий код из main, а затем приклеивает ваши коммиты сверху. История получается идеально ровной, будто вы только что начали писать код на базе самого свежего проекта.

## 2. Какие инструменты Git используют в компаниях?
В реальной работе используется стандартный стек:

- Ветки по Git Flow или GitHub Flow: Есть главная ветка (main или master), ветка разработки (develop) и короткие ветки под задачи (feature/task-123, bugfix/fix-login).
- Pull Requests (или Merge Requests в GitLab): Код никогда не льется в main напрямую. Всегда создается PR, его смотрят коллеги (Code Review), проходят автоматические тесты (CI/CD), и только потом код мержится.
- Инструменты автоматизации: Пулл-реквесты на GitHub часто настраивают так, чтобы кнопка «Merge» блокировалась, пока код не обновится до актуального состояния main. Вот тут rebase или автоматический squash and merge и приходят на помощь.

## 3. Обязательно ли учить консоль или можно сидеть на UI (GitHub Desktop)?
- 90% ежедневных задач (add, commit, push, pull, создание веток) в GUI-интерфейсе делаются быстрее и нагляднее.
- Консоль нужно знать на базовом уровне («понимать, как это работает под капотом») по двум причинам:

   1. Сложные конфликты и факапы: если случайно закоммичен токен от базы данных, в консоли через git reflog или git reset --hard можно спасти проект за секунду.
   2. На интервью спросят: «В чем разница между merge и rebase?» или «Что делает git cherry-pick?».

* Нужно знать: Разницу между merge и rebase, что такое stash (заначка), как решать конфликты, как делать amend (исправление последнего коммита).

## 4. В какой ветке работать

**Правило:** писать код напрямую в ветку develop (или main) **нельзя**.
В develop всегда должен лежать стабильный, рабочий код, который в любой момент можно запустить.

**Как выглядит правильный процесс:**

   1. Переключаетесь на develop и скачиваете последние изменения команды (git pull).
   2. Отпочковываетесь от нее — создаете свою ветку под задачу (например, feature/login-page или bugfix/fix-Header).
   3. Кодите, делаете коммиты и пушите только в эту свою ветку.
   4. Когда задача полностью готова, вы создаете Pull Request (PR) из своей ветки в develop.
   5. Коллеги проверяют ваш код, и если всё ок, ваша ветка сливается (merge или rebase) в develop. Саму ветку под задачу после этого удаляют.

## 5. Можно ли сделать rebase на самом GitHub, а не в консоли?
В момент принятия Пулл-Реквеста (PR), варианты принятия:

- Create a merge commit (обычный мерж — то, что вы делали).
- Squash and merge (схлопывает все ваши мелкие коммиты в один и вливает в main).
- Rebase and merge (это и есть тот самый rebase! GitHub сам берет ваши коммиты и перебазирует их поверх актуального main, не создавая лишних коммитов слияния).

В консоли ребейз делают до создания PR, чтобы стянуть изменения из develop в свою ветку, решить конфликты локально на компе, убедиться, что проект собирается, и только потом заливать чистую ветку на GitHub.

## 6. Что делать с веткой после мержа?

Продолжать работу в старой ветке — это плохой тон (и технические грабли).
Когда вашу ветку влили в develop на GitHub, её миссия завершена. Если вы продолжите писать новый код в этой же ветке, у вас гарантированно возникнут проблемы:

   1. Вы запутаете коллег, потому что в Пулл-Реквесте смешаются старые (уже принятые) задачи и новый код.
   2. Начнутся дикие конфликты, так как ветка на сервере закрыта, а у вас на компьютере она живет своей жизнью.

Как это устроено в Git (про дубликаты веток):
Ветка в Git — это текстовый ярлык (ссылка) на конкретный коммит. Когда вы нажимаете кнопку "Delete branch" на GitHub после мержа, удаляется только ярлык на сервере. На компьютере этот ярлык (feature/...) остается, пока вы не удалите его вручную или через интерфейс.

Дубликатов не возникнет: если вы удалили ветку на сервере, стерли её локально и потом создали новую с таким же именем — для Git это будет абсолютно чистая новая ветка, созданная с нуля.
